# Подход к тестированию

## Цель

По документации метода (авторизация, тело запроса, таблица валидации, алгоритм работы) составить коллекцию Postman так, чтобы проверяющий мог запустить каждую проверку, подставив только свой токен авторизации.

## Что покрыто

| Папка | Запросов | Фокус |
|-------|----------|-------|
| Авторизация | 3 | Токен: получение, отсутствие, невалидный |
| Позитивные сценарии | 6 | Все ветки алгоритма (ИНН 10/12, с ОГРН и без, обязательные / все поля, несколько руководителей) |
| Валидация name | 5 | Отсутствие, границы длины |
| Валидация inn | 6 | Отсутствие, длина, формат, уникальность |
| Валидация ogrn | 6 | Обязательность при ИНН 10, длина, формат, поведение при ИНН 12 |
| Валидация address | 5 | Отсутствие, границы длины |
| Валидация phone | 5 | Форматы, длина |
| Валидация head | 16 | Массив, границы имени / фамилии / отчества |
| Валидация тела запроса | 4 | Пустой объект, нет тела, невалидный JSON, лишние поля |

**Итого: 56 запросов в 9 папках.**

## Техники

- **Граничные значения** для всех полей с ограничением длины: min−1, min, max, max+1.
- **Позитивные сценарии** по каждой ветке алгоритма, а не только happy path.
- **Негативные проверки** по каждому правилу таблицы валидации.
- **Проверки уровня запроса:** пустое и битое тело, неизвестные поля, авторизация.
- Именование кейсов: «Группа — что проверяем»; в description — цель, ожидаемый результат, условия запуска.

## Ограничения

- Часть кейсов зависит от предыдущих шагов (повторная регистрация, GET). Отмечено в названиях и описаниях. Улучшение: pre-request-скрипты.
- Не покрыты: несоответствия типов (число вместо строки), пустые строки vs отсутствие поля, один невалидный элемент в массиве head.
