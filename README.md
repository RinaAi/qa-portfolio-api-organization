**Задача:** по документации спроектировать коллекцию Postman для полного тестирования POST-метода создания организации.

Хост, токены и учётные данные убраны: принадлежат заказчику, публиковать нельзя. Ниже описан подход и результаты.

---

## Задача

По документации метода (авторизация, тело запроса, таблица валидации, алгоритм работы) составить коллекцию Postman так, чтобы проверяющий мог запустить каждую проверку, подставив только свой токен авторизации.

---

## Что сделано

Коллекция из **56 запросов** в **9 папках**:

| Папка | Запросов | Что проверяется |
|-------|----------|-----------------|
| Авторизация | 3 | Получение токена, запрос без токена, запрос с невалидным токеном |
| Позитивные сценарии | 6 | Все ветки алгоритма: ИНН из 10 и 12 цифр, с ОГРН и без, только обязательные поля, все поля, несколько руководителей |
| Валидация name | 5 | Отсутствие поля, границы длины |
| Валидация inn | 6 | Отсутствие, неверная длина, нецифровые символы, повторная регистрация |
| Валидация ogrn | 6 | Обязательность при ИНН из 10 цифр, неверная длина, буквы, поведение при ИНН из 12 цифр |
| Валидация address | 5 | Отсутствие поля, границы длины |
| Валидация phone | 5 | Допустимые форматы, неверный формат, неверная длина |
| Валидация head | 16 | Отсутствие и пустой массив, границы длины имени, фамилии и отчества |
| Валидация тела запроса | 4 | Пустой объект, отсутствие тела, невалидный JSON, лишние поля |

---

## Подход

- **Граничные значения** для всех полей с ограничением длины: min-1, min, max, max+1.
- **Позитивные сценарии** по каждой ветке алгоритма метода, а не только «счастливый путь».
- **Негативные проверки** по каждому правилу таблицы валидации: отсутствие обязательного поля, неверный формат, неверная длина.
- **Проверки уровня запроса:** пустое и битое тело, неизвестные поля, авторизация.
- Каждый кейс назван по шаблону «Группа - что проверяем» и описан в поле description: цель, ожидаемый результат и условия запуска.

---

## Найденные дефекты

### 1. Невалидный токен → 500 вместо 401

- **Шаги:** отправить запрос с заведомо некорректным Bearer-токеном.
- **Ожидаемый результат:** 401 Unauthorized.
- **Фактический результат:** 500 Internal Server Error.
- **Влияние:** клиент не может отличить ошибку авторизации от сбоя сервера; ошибка скрывает причину проблемы.

### 2. Расхождение документации и реализации по ОГРН

- **Документация:** таблица валидации требует 13 цифр для любого заполненного ОГРН; алгоритм описывает проверку только для ИНН из 10 цифр.
- **Проверка:** запрос с ИНН из 12 цифр и невалидным ОГРН (14 цифр).
- **Результат:** организация создаётся (200), невалидный ОГРН принимается.
- **Вывод:** реализация следует алгоритму, а не таблице валидации. Требования нужно уточнить у аналитика.

---

## Ограничения и что можно улучшить

- Часть кейсов зависит от предыдущих шагов (повторная регистрация, проверка сохранения через GET). Это отмечено в названиях и описаниях. Способ сделать их независимыми: pre-request-скрипты для создания данных.
- Не покрыты: несоответствия типов данных (например, число вместо строки), пустые строки отдельно от отсутствующих полей, массив руководителей с одним невалидным элементом.

---

## Инструменты и навыки

Postman, анализ требований, тест-дизайн (граничные значения, классы эквивалентности), оформление баг-репортов.
